# waac-rs

Rust port of WAAC (arXiv:2611.08865, "Rethinking Agent Trajectory
Compression: A Workflow-Aware Perspective"), the agent-track session
in this directory. The Python version is VERIFIED (CPU test passes,
verdict SUPPORTED); this is the standing-rule Rust second stage
(2026-11-02): same mechanism, same experiment, same assertions, run
live in Rust and checked against Python case by case.

Std-only, deterministic, no network, no model calls — like the Python
reference (`waac.py`, `corpus.py`, `test_waac_cpu.py`).

## What is ported

| Python | Rust |
|---|---|
| `waac.py` policies / `fuse` / `fuse_many` / `policy_satisfies` | `src/policy.rs` |
| `waac.py` `Field` / `OpNode` / `TraceDAG` / obligations / `online_requirements` | `src/waac.rs` |
| `waac.py` fragments / `canonical_key` / TF-IDF / `HistoryLibrary` | `src/waac.rs` |
| `waac.py` `fuse_policies` / `project_field` / `effective_caps` / `project_context` | `src/waac.rs` |
| `corpus.py` seeded workflow generator | `src/corpus.rs` |
| `test_waac_cpu.py` executor + baselines + aggregate | `src/executor.rs` |
| `test_waac_cpu.py` main experiment + checks A1–A7 | `src/main.rs` (`waac-verify`) |
| `hashlib.sha256` (for `canonical_key`) | `src/sha256.rs` (hand-written, std-only) |
| `random.Random` (corpus + property-check seeds) | `src/mt19937.rs` (CPython-compatible MT19937) |
| `json.dump` / `json.load` (results + parity cases) | `src/json.rs` |
| CPython `sum()` over floats | `py_sum` in `src/lib.rs` (Neumaier) |

`waac-parity` (`src/bin/parity.rs`) is the parity harness: it reads
JSON cases generated by `tests/parity_check.py`, runs the mechanism,
and prints JSON results for exact comparison against `waac.py`.

## Build and test

```bash
cargo test --offline        # 27 tests: 17 unit + 10 deep (see below)
cargo build --release --offline
./target/release/waac-verify            # live-test verification
./target/release/waac-verify out.json  # ... to a chosen path
python3 tests/parity_check.py                       # parity sweep, seed 20261109
python3 tests/parity_check.py --seed 777           # ... second seed
python3 tests/parity_check.py --seed 12345         # ... third seed
```

The `waac-verify` binary is 970 KB; `verify` runs in ~0.13 s
(release). The Python test takes ~0.35 s for the same experiment.

## Deeper tests (2026-11-09, `tests/deep.rs`)

Beyond the `verify` experiment, a fixed-seed (splitmix64) suite:

- **Fusion property, 5000 random triples:** associativity,
  commutativity, never-relaxes, and equality with an independent
  capability-union oracle; plus all 341 policy sequences of length
  ≤ 4 checked exhaustively against the same oracle.
- **Online requirements, 2000 random DAGs:** obligations and
  requirements checked against oracles written directly from the
  Sec. 3.3.1 spec; every requirement covers the union of its
  obligations' capability sets.
- **Fusion never relaxes, 2000 random requirement sets:** random
  online requirements + random history proposals; fused caps ⊇ online
  caps for every field, and fused == oracle join.
- **Projection truth table, 2000 random cases:** (policy, long_text,
  artifact present) → rendered text, fallback flag, and effective
  caps all match the App. A.3 table; SUMMARY stubs are exactly 25
  tokens + marker.
- **History matching, 2000 random queries:** scores in [0, 1];
  exact queries hit exact at 1.0; coarse only when ops + field roles
  match; the 0.5 threshold is respected (a no-match at 0.5 has best
  score < 0.5 when re-run at threshold 0.0).
- **Soak, 600 workflows (fresh seeds, 10× the Python corpus):**
  WAAC-full 600/600, no-compression 600/600, 100% gold retention at
  every step, 728,572 vs 3,381,697 tokens, 5,402 history lookups.
  All 7 methods run to completion on all 600.
- **Soak, 12,000 history lookups** against the real 25-entry library:
  exact 4,350, coarse 3,650, none 4,000; no panic, no invalid score.
- **Threads:** 8 threads × parallel `waac_full` runs + fusion sweeps
  return results identical to the sequential run; history matching is
  pure (same fragment, same answer, 100 repeats).

Full run: **27/27 tests pass** (17 unit + 10 deep; ~15 s, dominated
by the 600-workflow soak).

## Deliberate divergences from Python

Every difference from the Python reference is listed here;
undocumented divergences would fail this leg.

1. **Corpus RNG is a CPython MT19937 port, not a new RNG.**
   `src/mt19937.rs` reproduces `random.Random` bit-for-bit
   (`init_by_array` seeding from the int seed's little-endian 32-bit
   words, `random()` from two `genrand_uint32` outputs, `_randbelow`
   rejection sampling, Fisher-Yates `shuffle`). Validated by the
   byte-identical `results.json`, not just by unit tests. The corpus
   generator's RNG call order mirrors `corpus.py` line by line,
   including argument-evaluation order (`randint` before the
   `_long_text` call that consumes it).
2. **SHA-256 is hand-written** (`src/sha256.rs`, std-only) instead of
   `hashlib`. Verified against `hashlib` vectors (`""`, `"abc"`,
   the 56-byte FIPS vector, 1 MiB of `'a'`); canonical keys match
   Python exactly (e.g. workflow 0, ops 0–4: `aacdc5c7643ccb1f`).
3. **Float summation is Neumaier, not naive.** CPython 3.12's
   `sum()` uses Neumaier compensated summation; Rust's `.sum()` is
   naive left-to-right and differs in the last ulp on the aggregate
   ratios. `py_sum` (`src/lib.rs`) implements Neumaier and is used
   wherever Python sums floats: `aggregate`, the TF-IDF norm, and
   the cosine. This was found empirically: the first Rust run matched
   every integer but differed in the last ulp on four aggregate
   ratios and the coarse-match score; Neumaier closed all of them.
4. **TF-IDF vectors are insertion-ordered `Vec`s, not dicts.**
   Python dicts preserve insertion order and the cosine sum follows
   it; Rust `Vec<(String, f64)>` preserves first-occurrence order
   for the same rounding. `HashMap` is used only for lookups (idf
   map, runtime state, exact-key index) — never for order-sensitive
   iteration. All order-sensitive maps are `BTreeMap`s.
5. **`f64::ln` vs `math.log`.** Both call the system libm on this
   machine; verified bit-identical on every value exercised (the
   A7 coarse score is exactly 1.0 in both, and the parity sweep
   compares TF-IDF scores with exact float equality, 0 mismatches).
6. **Float formatting.** `py_float_str` (`src/corpus.rs`) uses Rust
   `{:?}` for f64, which matches Python `repr` for the value range
   used here (shortest round-trip, `.0` for integral floats). The
   two differ only in exponent format for values < 1e-4 or ≥ 1e16,
   which never occur in this corpus or in `results.json` (verified
   by the byte-identical diff). The `json` module's float writer
   uses the same formatting.
7. **Duplicate field names within one op.** Python stores
   `OpNode.outputs` in a dict, so a duplicate name silently
   overwrites; Rust stores a `Vec<Field>` in insertion order and
   keeps both. The corpus never produces duplicates, and
   `make_fragment` sorts by field name exactly as Python does, so
   this cannot affect the experiment. The parity generator was fixed
   to sample distinct field names per op after this difference
   surfaced as 60 mismatches in the first sweep run.
8. **Cosine can exceed 1.0 by rounding.** The cosine of two
   identical normalized vectors is 1.0 up to float rounding
   (1.0000000000000002 is possible in both implementations — same
   arithmetic, same result). Deep tests allow ±1e-9 around [0, 1];
   the parity sweep compares scores exactly and still reports 0
   mismatches.
9. **`verify` output filename.** `waac-verify` writes its raw
   Python-shaped output to `verify_results.json` by default (not
   `results.json`), so re-running it never clobbers the curated
   `results.json` record in this directory, which also carries the
   deep-test and parity numbers.
10. **No `target/`, no binaries, no secrets in this directory.**
    The crate has zero dependencies (`Cargo.lock` lists none), so
    `cargo build --offline` needs no network. Nothing model-backed,
    networked, or GPU was ported — there is none in the Python
    reference.
11. **`online_requirements` keeps Python's signature.** Python
    ignores its `dag` argument (obligations already carry sources);
    Rust takes `_dag` and does the same mapping. No behaviour change.
