# Rust second stage — Student-Aware Teaching (arXiv:2611.13144)

Rust port of the Python mechanism in `../student_teaching.py`, built under
the standing Rust-second-stage rule (2026-11-02). The Python version stays
the primary verdict carrier; this port never replaces it.

## What is ported

`src/lib.rs` is a line-for-line port of the pure logic, no external crates:

- `SplitMix64` — identical arithmetic, so task streams match Python exactly.
- Task generation (`gen_tasks`, `gen_task`, `gen_probe_task`) — same seeds,
  same op sequences, same gold answers.
- `StudentAgent::solve` — the same call accounting, including the exact
  spend semantics (a budget failure inside `do_read` returns *without*
  appending `"budget_exhausted"`, matching Python).
- `Teacher` — profile (with the same spurious-fingerprint RNG consumption
  order), probes, admission gate — plus `profile_free_teach`,
  `profile_only_teach`, `misleading_teach`.

## Deliberate divergences from Python

1. `Teacher::probe` seeds probe tasks with a fixed constant instead of
   Python's `hash(lim) % 1000`: CPython string hashing is randomized per
   process, but the seed is unused — probe tasks are fixed per limitation,
   so the tasks (and outcomes) are identical either way.
2. Dict/set iteration order: Python `set` iteration is nondeterministic
   in principle, but the module only uses sets for membership and counting
   (addition commutes), so results are order-independent. Rust uses
   `BTreeMap`/`BTreeSet` (sorted) and `Vec` (insertion order) where order
   is observable.
3. `f64` conversion of a `u64` uses the same round-to-nearest-even rule in
   both languages, so `SplitMix64::random` streams match exactly.
4. `randbelow` compares in `u128`: for `n == 1` the rejection limit is
   2^64, which wraps to 0 as `u64` and would loop forever (a `choice()` on
   a 1-element slice calls `randbelow(1)`). Python computes the same limit
   in bigint. This was a real hang found during the port (fixed before any
   test ran green).

## Live extensive test (all run live)

```
cargo test --release
```

- **17 tests, all passing:** 11 unit (SplitMix64 vectors from Python,
  task determinism/shape, probe isolation per limitation, admission gate
  admits-real/rejects-spurious, profile finds true limitations, budget
  arithmetic, skill texts), 5 deep (exhaustive 32 limitation subsets
  against the probe oracle, property sweeps over seeds, 2,000-task soak,
  thread-identity), 1 parity sweep.
- **`verify` binary** (`cargo run --release --bin verify`): mirrors the
  Python CPU test's experiments and assertions A1–A7. It reproduces the
  Python numbers **exactly**: untaught_A 0.400, profile_free_A 0.715,
  profile_only_A 0.780, sat_A 0.955, sat_B 0.980, A_with_B 0.400,
  B_with_A 0.520; libraries `["L1","L3","L5"]` / `["L2","L4"]`;
  misleading admits `[]`; probe accuracy 1.0. All A1–A7 pass. Writes
  `results.json`.
- **Parity sweep:** 1,200 cases (5 seeds × 40 tasks × 6 student
  configurations) replayed from `tests/parity_reference.txt` (generated by
  the Python module): task shape (gold, traps, op count) and solve outcome
  (success, calls, fingerprints in order) — **0 mismatches**.

## Soak / scale notes

- 2,000-task soak: a clean student solves ≥0.99; the only failures are the
  ~0.2% of tasks needing 15 calls against `BASE_BUDGET=14` (flaky retries
  on two keys + stale re-read), i.e. budget failures, never wrong answers.
- Thread-identity: the same 200-task batch solved on 4 threads gives
  byte-identical results to the single-threaded run (the student is
  stateless across tasks).

## How to run

```bash
cargo test --release        # unit + deep + parity
cargo run --release --bin verify   # main experiment, writes results.json
```

No `target/`, no binaries, no secrets are committed from this directory.
